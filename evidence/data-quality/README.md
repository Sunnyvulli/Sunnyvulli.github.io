# Data Quality Gate: CSV → validated SQLite → audit report

Foundational portfolio exercise using synthetic orders. This is a runnable learning sample, not employer work or a production deployment. See projects/mobility-quality for the real-data flagship project.

## Problem
A reporting pipeline should not silently accept duplicate orders, invalid dates, missing identifiers, or malformed currency. This example separates valid records from rejected ones, records why each rejection occurred, and reconciles accepted data with SQL aggregates.

## Run locally
Requires Python 3.10+; uses only its standard library. Download this folder or clone the repository, then:

```sh
cd evidence/data-quality
python -m unittest -v
python pipeline.py --input orders.csv --database orders.sqlite --report report.json
```

## Observed result
The committed 10-row fixture produces 4 accepted rows and 6 rejected rows. Accepted currency totals 24,025 cents ($240.25). These are fixture results, not performance benchmarks. The checked-in report.json was generated by running the pipeline.

## Design decisions
- Currency uses Decimal for validation and integer cents for storage, avoiding binary floating-point rounding. Non-finite, negative, sub-cent, and out-of-range values are rejected.
- The first **valid** occurrence of an order ID wins. An earlier rejected record does not reserve that ID.
- A single database transaction replaces the accepted snapshot; reruns do not append duplicates.
- Rejected records retain CSV line numbers and reason codes. A record can have multiple reasons; reason counts need not equal rejected row count.
- SQL groups accepted orders by date and reconciles counts and totals.

## Verification
Four unittest cases check fixture totals/rejection reasons, deterministic reruns, numeric boundaries plus invalid-first duplicates, and preservation of an existing database when an invalid schema is supplied.

## Limits and next experiments
Input is loaded into memory, so this is not a large-scale streaming design. The report file is written after the database commit; those two outputs are not one atomic transaction. A production design needs versioned batches, schema evolution, access controls, observability, and recovery procedures. Customer IDs are checked for presence, not against a reference customer table. No cloud scalability or throughput claims are made.

A proposed research extension would systematically inject missing values and duplicates at different rates and measure changes in aggregate error, rejection coverage, and runtime. This experiment has not been conducted.

## Interview discussion
Explain why integer cents help, why silently dropping rejected records harms auditability, when snapshot replacement is unsuitable, and how to extend this to incremental processing. Read and run the code before presenting it as part of an interview.
